# Data

All paths are resolved by `src/util/project_paths.m`; the pipeline never looks
for data by bare file name on the MATLAB path. `setup_paths()` warns at
startup about any missing file, and the function that needs it errors with the
full path it looked for.

## raw/ (tracked, read-only)

| File | What it is |
|---|---|
| `lv_grids.mat` | The grid portfolio. One MATLAB struct `data` holding, per network, a table of line segments (`LV_grid`, 1116 tables: from/to node names, line id, length, R and X per km, ampacity, peak P and Q per node, existing PV) and a table of its MV/LV substation (`MV_LV_sub`: transformer rating and per-unit impedance, side voltages, switch states), with the ids in `LV_grid_id` / `MV_LV_sub_id`. It also carries MV-level tables (`MV_grid`, `MV_station`, `MV_HV_sub`) that the current pipeline does not use. MATLAB tables are stored as class objects, so the file is readable only from MATLAB. Formerly `LV_data/data_v2.mat`. |
| `pv_profiles_year.mat` | One year of normalised PV output (per unit of installed DC peak) at 15-min resolution, two series: `pv_norm_clearsky` (ideal clear sky) and `pv_norm_measured` (PVGIS typical meteorological year), plus `time_iso` and `meta.timestep_minutes`. Produced with pvlib (haydavies transposition, ineichen clear-sky, faiman cell temperature) outside this repository. |

The scenario-dependent PV and EV columns (`PV_kW_`, `EV_count`) are **not**
stored in `lv_grids.mat`. `allocate_PV_EV_SFOE` adds them in memory at every
run from the SFOE scenario table in `config/general_config.json`, and the
portfolio runner saves the result into the run folder as
`allocation_<scenario>.mat`.

Provenance of the grid data (network operator, extraction date, any usage
restrictions) is not recorded anywhere in the repository. Fill this in before
sharing the repository further.

## external/ (not in git)

| File | Size | Needed by |
|---|---|---|
| `load_consumption_train_heapo.mat` | 163 MB | `generate_load_profile` (via `generate_nodal_scenarios_4`). Required even when `demand_profile.enabled = false`, because the native time resolution of the demand stream is read from it. |

Training set for the in-house GMM load-profile sampler (see
`docs/load_simulator_final.pdf`). One variable `training_data` with fields
`X` (steps per day x days x houses), `time` and `cluster_idx`.

**Where to get it:** not recorded in the repository. Ask the repository owner
and put the file in this folder.

## derived/ (tracked caches)

| File | What it is | Regenerated by |
|---|---|---|
| `violation_ids_sc1_2040.mat` | Variable `viol_converged_single_tr_ids`: the single-transformer networks (236) whose base-case temporal load flow converged and showed a voltage or current violation under scenario `sc1_2040`. This defines the `"ALL"` portfolio in `main.m`. Formerly `LV_data/violation_converged_ids_sc1_2040.mat`. | **No script in the repository**; it predates the current pipeline. `load_ess_selection_context` looks for `violation_ids_<scenario>.mat` and falls back to this file with a warning for any other scenario. |

### load_gmm/

`load_gmm_model` caches the fitted demand GMM here, one file per fit-parameter
set (the file name spells the parameters out, e.g.
`load_consumption_train_heapo__K5_G4_log1_clip1_p0-99_all_all_seed1.mat`).
Fitting needs the training file in `external/` and the Statistics toolbox; sampling needs neither (the mixtures are stored as plain weight / mean / Cholesky arrays). Each file is
a few MB, and tracking it lets a clone generate demand without the training
set. The byte size of the training file used is stored inside and re-checked
when that file is present.
