## What this project does

Optimal siting, sizing, and technology selection of Energy Storage Systems (ESS) across a portfolio of Low Voltage (LV) distribution networks in the Sion/Sierre region of Switzerland, under SFOE energy transition scenarios (2030/2040). The optimization determines: which nodes to install storage at (siting), how large to make each unit (sizing), which technology to choose, and the dispatch schedule — all subject to voltage, current, transformer, and ESS operational constraints.

Technology parameters live in a dedicated JSON file (`util/technology_cfg.json`), the CVX formulation is isolated in `util/solve_ess_milp.m`, and the solver output includes a full explanation/reporting layer for technology choice via `util/analyze_tech_selection.m`.


## Running the optimization

This is a MATLAB project with no build step. Open MATLAB in the project root and run:

```matlab
main.m                  % Single-stage ESS technology-selection MILP
```

`addpath(genpath(pwd))` at the top of each entry point adds all subdirectories to the path automatically; `main.m` immediately follows it with `rmpath(genpath(fullfile(pwd, 'old-code')))` so `old-code/` is never on the path — anything still needed by the active pipeline cannot silently hide there. **Requires CVX and Gurobi** (`cvx_solver gurobi_3` is set inside `util/solve_ess_milp.m` — the active solve function, see Optimization loop below. `gurobi_3` is CVX's registered-solver name and does not need to match an installed Gurobi major version — on a machine with multiple Gurobi installs, `cvx_solver` with no argument lists what CVX resolves `gurobi_2`/`gurobi_3`/... to. Without this line active, CVX silently falls back to its default (SDPT3), which cannot solve the MILP's integer `I`/`ct` variables and fails opaquely).

> **Note**: `main_two_stage_OPF.m` (two-stage LP→MILP pipeline) has been removed. Its utility functions (`solve_lp_relaxation`, `extract_lp_candidates`, `run_seq_lin_loop`, `assemble_output_struct`) were unreferenced by any active entry point and have been moved to `old-code/` along with all other non-dependent functions (see Directory layout below). The former `_v2` files (`solve_ess_milp_v2.m`, `build_sensitivity_matrices_v2.m`, `combined_lv_sub_SFOE_v2.m`) have since been promoted to the canonical names (`solve_ess_milp.m`, `build_sensitivity_matrices.m`, `combined_lv_sub_SFOE.m`); their pre-sparsity-fix predecessors were moved into `old-code/` under their original names, alongside newly-identified dead code (`combined_lv_sub.m`, `plot_topology.m`, `generate_nodal_scenarios.m`, `generate_nodal_scenarios_2.m`, `getSCs_slack_correction.m`) confirmed to have zero callers in the active tree.

The technology-selection path uses `util/technology_cfg.json` plus `util/load_ess_selection_config.m` to provide technology-specific C-rate, efficiency, and cost inputs.

`main.m` is a thin driver: it owns three run knobs and delegates everything else to `util/load_ess_selection_context.m` and `util/run_ess_selection_portfolio.m`.

```matlab
network_id   = "LV_Grid_71590";   % LV_Grid id(s) to run, or "ALL" for the full sane portfolio
horizon      = [];                 % [] = full day; e.g. 1:32 for a short intra-day debug window
enable_plots = true;               % temporal-profile / tech-selection / losses diagnostic figures
```

The simulated day count `D` and the time-step `Ts_h` are **not** `main.m` knobs — they live in `util/sizing_cfg.json` under `"horizon": { "days", "Ts_h" }`. `load_ess_selection_config` derives `steps_per_day = 24 / Ts_h` and the run length is `T = days * steps_per_day`. `Ts_h` must match the native resolution of the demand/PV/EV input data (15-min → 96 steps/day); `build_temporal_profiles` errors loudly if it doesn't.

To run the full violation-flagged portfolio, set `network_id = "ALL"` (resolves to `ctx.sane_net_indices` inside `run_ess_selection_portfolio.m`).

For parallel execution across 4 MATLAB sessions, set `run_opts.allow_mult_instances = true` and change `run_opts.instance_id` (1–4) in each session (only applies when `network_id = "ALL"`).

| File | Description |

### Single-stage pipeline call chain

`main.m` no longer inlines the portfolio loop, per-network preprocessing, or the
sequential-linearization loop — those live in `util/`:

```
load_ess_selection_context(scenario)                       [util/]
    loads LV_data/data_v2.mat + violation ids + general_config.json,
    builds cfg via load_ess_selection_config, allocates PV/EV via
    allocate_PV_EV_SFOE, computes sane_net_indices
    └─► run_ess_selection_portfolio(ctx, network_id, horizon, enable_plots, run_opts)  [util/]
            resolves network_id ("ALL" -> ctx.sane_net_indices, honoring the
            4-way multi-instance split; otherwise ismember lookup), opens the
            run log, loops networks with try/catch, saves into the matching
            out_dir_* folder based on returned status
            └─► solve_network_tech_selection(ctx, n_idx, horizon, enable_plots, run_opts)  [util/]
                    one network, no file I/O: seeds rng, calls
                    preprocess_network (below), runs check_voltage_guard,
                    then the seq-lin loop
                    └─► run_seq_lin_loop_ess(gm, dims, grid_params, opts, cfg, ...)  [util/]
                            per-iteration build_sensitivity_matrices +
                            solve_ess_milp + OPF_verification; on each
                            voltage-error improvement, calls
                            build_network_result to assemble `out` and
                            (if enable_plots) analyze_tech_selection/analyze_losses
```

### Configuration

- [util/general_config.json](util/general_config.json) — PU base values (`Sb=100kVA`, `Vb=230V`), demand/generation factors, SFOE scenario parameters (population ratios, PV/EV targets)
- [util/sizing_cfg.json](util/sizing_cfg.json) — converter/transformer box coefficients, a `horizon` block (`days` = simulated-day count `D`, `Ts_h` = time-step in hours; `steps_per_day = 24/Ts_h` and `Ts_h` are derived/mirrored into `cfg.solver.Ts_h` by `load_ess_selection_config`), solver flags (`VOLT_CONV_THRESH`, `VMAG_LB/UB`, `current_mag_cstr`, `flags.curtailment_activate`), and `economics` (CHF/kWh prices for transformer losses and PV curtailment — `curtailment_price_CHF_per_kWh` is a placeholder, not a calibrated tariff); base config loaded by `load_ess_selection_config`, which merges it with `technology_cfg.json`
- [util/technology_cfg.json](util/technology_cfg.json) — Li-ion and Na-ion technology-specific C-rate, efficiency, bounds, and cost inputs for the new ESS selection path

### Optimization loop

The AC OPF is non-convex, so it is solved by sequential linearization:

1. **Sensitivity assembly**: `build_sensitivity_matrices(gm_curr, AUX_to_all_nodes, AUX_to_all_nodes_PV, dims)` assembles block-diagonal `dVmagdP`, `dImagdP`, etc. over all T timesteps. Post-restructure it reads the `[rows x N x T]` sensitivity arrays directly: `pagemtimes` projects each page N→Nd (or N→Npv for the PV variants) in one batched matmul, then a single `sparse(...)` scatter places the T reduced blocks on the diagonal — no `cellfun(@sparse)`, no `blkdiag` of T blocks, no dense `[NT x NT]` intermediate. Output `sens.*` (sparse double, same field names/shapes) is byte-identical to the old cell+blkdiag path in double precision; `gm.lm` is stored `single`, which adds ~6e-8 relative (linearization tolerance is 1e-2). The pre-sparsity-fix predecessor is archived at `old-code/build_sensitivity_matrices.m`.
2. **CVX solve**: `solve_ess_milp(sens, prev, dims, cfg, grid_params, opts)` expresses voltage, current, and slack bus constraints as linear functions of ESS injection increments `dB_plus`, `dB_minus`, plus (if `opts.curtailment_activate`) a PV curtailment term `P_curt` (see PV curtailment below). The MILP selects technology via binary `I(Nd, J)` with Big-M linking, enforcing at most one technology per node — that last constraint (`sum(I(n,:)) <= 1`) is switchable via `cfg.flags.one_tech_per_node` (`util/sizing_cfg.json`, default `true`; `solve_network_tech_selection.m` copies it into `opts.one_tech_per_node`; `solve_ess_milp.m` treats a missing field as `true`, because many `experiments/` scripts hand-build `opts`). With `false`, a node may host both technologies as two independent units (each with its own `E_nom`/`S_conv`/dispatch and its own `cI` installation cost), and it only applies when `siting_activate` is on. Downstream code that loops over `Installation` per `(n,j)` is fine; anything doing `find(Installation(n,:),1)` assumes one technology per node — see `experiments/one-tech-per-node-study.md`. The objective trades off battery capex (`costE`, `costS`), install cost (`costI`), transformer/slack losses (`costL`), and curtailed energy (`costCurt`) — all in the same linear objective, so the solver genuinely compares them against each other. (The archived `old-code/solve_ess_milp.m` is the same formulation but with the SOE evolution written as `SOE_0 + Ts*cumsum(...)` instead of the active file's sequential per-step recursion — see Long-horizon sparsity below.)
3. **Verification**: `OPF_verification` re-runs nonlinear FPI load flow to measure linearization error.
4. **Re-linearize**: `re_linearization` recomputes sensitivity matrices at the updated operating point for the next iteration.
5. **Best solution**: The iteration with minimum voltage linearization error (`v_err`) is saved, not necessarily the lowest-cost iteration.
6. **Analysis**: `analyze_tech_selection(out, cfg)` generates three diagnostic figures explaining technology choice (see Technology reporting below); `analyze_losses(out, cfg)` covers BESS/transformer active/reactive losses; `analyze_voltage_current(out)` covers nodal voltages and line currents (pu of ampacity), initial operating point vs. solved linear model vs. solved nonlinear load flow; `analyze_curtailment(out, cfg)` (gated by `opts.curtailment_activate`) covers PV curtailment specifically — see PV curtailment below.

### Key struct layouts

**`gm` (linear grid model)**
- `gm.grid` — raw grid struct (Y matrix, ampacities, nominal power, etc.)
- `gm.lm.*` — **contiguous arrays** (NOT `{1xT}` cells — restructured for the O(T²) fix, see Long-horizon sparsity):
  - 0-order: `P0`,`Q0`,`Vmag0`,`Vmag_dxdVsmag` `[N×T]`; `Vsmag0`,`Ss_dxdVsmag` `[1×T]`; `Imag0` `[L×T]` complex; `Ss0` `[1×T]` complex
  - sensitivities: `Vmag_dxdP`,`Vmag_dxdQ` `single [N×N×T]`; `Imag_dxdP`,`Imag_dxdQ` `single [L×N×T]`; `Ss_dxdP`,`Ss_dxdQ` `[1×N×T]` complex; `I_dxdP`,`I_dxdQ` `single complex [L×N×T]` **or `[]`** (only stored when `keep_complex_I`, i.e. `cfg.solver.current_mag_cstr == false` — otherwise `solve_ess_milp` never reads them; halves `gm.lm` memory)
  - `gm.lm.keep_complex_I` (logical), `gm.lm.tim_colec` (`[1×T]` per-timestep loop wall time)
  - **Read 0-order fields via `lm_stack(x)`** (`util/lm_stack.m`) — returns the array as-is, or `[x{:}]` for legacy `{1xT}` cell results saved before the restructure. All `analyze_*` / `plot_gm_temporal_profiles` use it.
- `gm.nodal_injections_D_pu` — [T × Nd] demand injections in pu

**`out` (saved result per network)**
- `out.summary` — status, total E/S, errors, timing
- `out.sizing` — per-node `E_nom_node_pu` [Nd×J], `S_conv_node_pu`, `Installation` binary,
  `SOE_0_pu` [Nd×J] (cyclic-boundary state-of-energy decision variable from `solve_ess_milp`),
  `demand_node_id` [Nd×1] (row k → full topology node index; `find(nodes_with_demand) + 1`,
  the `+1` recovering the slack bus dropped when `nodal_nominal_power` etc. were built — see Node indexing below),
  `pv_node_id` [Npv×1] (same `+1` convention, over PV-bearing nodes instead of demand nodes)
- `out.injections` — `B_bat`, `B_plus`, `B_minus`, `Q_ess`, `delta_P`, `delta_Q`, `P_curt` [T·Npv×1] curtailed PV, pu,
  `P_sloss` [T×1] transformer/feeder loss proxy (same quantity costed by `costL`)
- `out.costs` — `.E .S .I .L .Curt .total`, the solved objective's cost terms (CHF, per `cfg.economics`/`cfg.tech` pricing), packed straight from `solve_ess_milp`'s `sol.costs`
- `out.grid` — `vmag_lin`, `V_lf`, `Imag_lin`, `I_lf` (linearized and load-flow verified)
- `out.diagnostics` — per-iteration voltage/current errors, costs, statuses
- `out.meta` — scenario, config parameters
- `out.gm` — full grid model (large; placed last for `.mat` save efficiency)
- `out.cfg` — the exact `ctx.cfg` used for this solve, stamped in by `run_ess_selection_portfolio.m` right before saving. Lets any saved result be re-analyzed later (`analyze_*(out, cfg)`) without depending on the live state of `sizing_cfg.json`/`technology_cfg.json` — e.g. a file can be handed to `experiments/tech-selection-result-analysis/` (see below) and analyzed there with no other repo state needed.

## Important conventions

**Per-unit system**: `Sb = 100 kVA`, `Vb = 230 V` (single-phase). Energy `E_nom` in pu × 100 × 3 = kWh (three-phase). Power similarly.

**Node indexing (`N`) excludes the slack bus**: `get_grid_SFOE.m` builds `nodal_nominal_power`, `nodal_PV_SFOE`, `nodal_N_EV` from `nodal_demand_all(2:end, :)`, dropping row 1 — the slack bus is always full-topology index 1. So `N = numel(grid.nodal_nominal_power)` = (topology node count − 1), and every N-space array downstream (`gm.lm.Vmag0`, `Imag0`, `out.grid.vmag_lin`, etc.) is indexed 1..N corresponding to full topology index 2..(N+1). To recover the real node ID (e.g. to match `grid.graph_data.node_names`), add 1. Diagnostic plots (`analyze_tech_selection.m`) label nodes via `out.sizing.demand_node_id`, which already carries this `+1` shift — never label with the raw `sel_nd`/Nd-space row index directly.

**Mapping matrix `make_M`**: `make_M(nodes_with_demand)` builds a selector matrix from demand-only nodes to all nodes. `pinv(make_M(...))` is the expansion used everywhere to project Nd-dimensional vectors to N-dimensional.

**`AUX_to_all_nodes`**: Block-diagonal repetition of `pinv(make_M(...))` over T timesteps, produced by `repeat_block_diag` as `kron(speye(T), sparse(to_all_nodes_D))` — **sparse**, `O(T)` memory. Used to map [T·Nd] BESS injection vectors to [T·N] all-node vectors before multiplying by sensitivity matrices.

**`R_TNd_toNdT`**: Reshape permutation matrix from [T×Nd] column-stacked ordering to [Nd×T] ordering, produced by `linear_reshape_test` as a directly-constructed `sparse(...)` permutation — **sparse**, `O(T)` memory. Required because CVX variables and sensitivity matrices use different stacking conventions.

**BESS warm-starting**: `B_plus = B_plus_prev + dB_plus`. CVX solves for increments; the absolute values are reconstructed. On iteration 1, `B_plus_prev = 0`.

**PV curtailment (`Npv` node-space)**: BESS siting/dispatch is defined over demand nodes (`Nd`); PV curtailment is a separate, parallel decision defined over PV-bearing nodes (`Npv`, from `nodes_with_PV = grid.nodal_PV_SFOE > 0`) — these node sets aren't guaranteed to coincide, so curtailment gets its own `to_all_nodes_PV`/`AUX_to_all_nodes_PV`/`R_TNpv_toNpvT` mirroring the demand-node versions (built in `preprocess_network.m`), and its own sensitivity terms `sens.dVmagdP_PV`/`dImagdP_PV`/`dSsdP_PV` (active-power only; `build_sensitivity_matrices.m`, gated by passing `AUX_to_all_nodes_PV` as its 3rd argument). In `solve_ess_milp.m`, curtailment is a single continuous variable `P_curt` box-constrained `0 <= P_curt <= PV_avail_pu` (no new binaries), entering `vmag`/`Imag`/`P_sl`/`Q_sl`/`P_sloss` only as `-P_curt` — since it's bounded below by 0, it can only ever *reduce* net injection at a PV node, so it can relieve an over-voltage/over-current caused by PV export but can never relieve (and would only worsen) an under-voltage/overload caused by demand. Gated by `opts.curtailment_activate && dims.Npv > 0`; warm-started via `prev.P_curt_prev` exactly like `B_plus_prev`. **Known gap**: `re_linearization.m` only re-derives the next iteration's operating point from the Nd-space injection, so a multi-iteration run (`MAX_LIN_ITER_milp > 1`) would re-linearize around the pre-curtailment PV output on iteration 2+ — harmless today since `MAX_LIN_ITER_milp = 1`, but would need `re_linearization.m` extended with an Npv-space update before relying on curtailment across multiple sequential-linearization iterations.

**`OPF_verification.m` must be given the curtailment adjustment too, or the "ground truth" is wrong**: `grid/OPF_verification.m` reruns the nonlinear FPI load flow to check the linearization (`v_err`/`i_err`, and to pick the "best" iteration). It takes an optional 3rd argument `Injections_PV` (`[T x Npv]`, real, `= -P_curt`) that it maps through its own internally-built `to_all_nodes_PV` (from `grid.nodal_PV_SFOE > 0`) and adds to the demand-node injection before calling `loadflow_FPIs`. `run_seq_lin_loop_ess.m` passes `-reshape(sol.P_curt, T, Npv)` (a plain `reshape` recovers `[T x Npv]` directly — no `R_TNpv_toNpvT` needed, since `sol.P_curt`'s node-major stacking already puts one node's full `T`-length run in each column). **If this argument is omitted, the verification silently reruns the load flow as if no curtailment happened** — the linear model (`sol.vmag`/`sol.Imag`, computed inside `solve_ess_milp.m` with the `pv_dV`/`pv_dI` terms) correctly reflects curtailment, but the "ground truth" wouldn't, making `analyze_voltage_current.m`'s nonlinear-load-flow panels show an inflated, physically-inconsistent current/voltage that wouldn't actually occur once curtailment is applied, and inflating `v_err`/`i_err` for any iteration where curtailment is active.

**BESS is real-power-only by design (`delta_Q == 0`)**: `solve_ess_milp.m`'s power-balance block has both `delta_Q == sum(dQ_ess, 2)` and an unconditional `delta_Q == 0` right after it — intentional: the goal is zero reactive injection from the BESS, not a bug. Combined with the Big-M tech-selection linking (only one technology active per node, so every other tech's `Q_ess` is already boxed to 0), this forces the active tech's `dQ_ess` to 0 too — i.e. `Q_ess` stays pinned at its (zero) warm-start value regardless of `kQ_conv`/`kP`. As a result, the `kQ_conv`/`kPF` box constraints on `Q_ess` (in the "converter PQ box" section) are currently vestigial — harmless, but only meaningful again if reactive dispatch is ever re-enabled by removing `delta_Q == 0`. One consequence worth knowing: `Q_sl`/`Q_sloss` still change between the initial operating point and the solved one even with `Q_ess ≡ 0`, because `Q_sl`'s formula has a P→Q cross term, `imag(sens.dSsdP) * (R * delta_P)` — real active-power dispatch (BESS or curtailment) still perturbs slack reactive power through the network's linearized R/X coupling, so `analyze_losses.m`'s reactive-power before/after panels can show a large gap even with zero reactive dispatch — that gap is expected, not an error.

**Charge/discharge exclusivity penalty (`cha_dis_penalty_eps`)**: when `opts.cha_dis_bin_activate = false`, `solve_ess_milp.m` substitutes a linear penalty for the exact Big-M/binary exclusivity constraint — a technique established in the storage-scheduling relaxation literature (Nazir & Almassalkhi, arXiv:2103.07846; Prat/Lusby/Pinson, arXiv:2508.12999). An earlier version of this term (`sum(sum(0.5*(B_plus+B_minus)))`) was unscaled and excluded from `costL`, causing it to compete with real investment costs and to grow unboundedly with horizon length — confirmed by direct measurement, see `docs/ch-dis-relaxation-scaling-study.md`. The fixed formula, present in both objective branches now that `costL` is included everywhere:
```matlab
penalty_unit_cost = cfg.solver.cha_dis_penalty_eps * min([cE(:); cS(:)]);
costPenalty = penalty_unit_cost * sum(sum(B_plus + B_minus)) / T;
```
`cha_dis_penalty_eps` (`util/sizing_cfg.json`, default `1e-3`) is a small fraction of the cheapest real per-unit tech cost; dividing by `T` keeps the term's *aggregate* objective share horizon-invariant. Validated clean (zero exclusivity violation, byte-identical sizing) from `eps=1e-6` through `1e-3` at small horizons. **Known limitation, not fixable by further `eps` tuning**: at full-year scale (`T=35,040`) a residual violation survives, confirmed (by direct inspection of the solved dispatch, not guesswork) to be driven by a specific technology's C-rate rather than an under-tuned penalty — `B_plus`/`B_minus` independently bound by `c_rate * E_nom` (not their sum), so a high-`c_rate` technology (NaIon, `c_rate=5`, vs. LiIon's `1.1`) has enough box slack to run both directions near-simultaneously at a handful of timesteps, and since `opts.min_loss=false` by default prices no round-trip-loss cost, the tiny penalty is the only disincentive and gets dominated by whatever feasibility benefit the LP extracts there. Increasing `eps` 10x changed nothing (see the write-up) — this rules out "penalty too weak." Sizing/siting is unaffected either way; it's a dispatch-level artifact confined to the high-C-rate technology. **Worth checking whenever a new technology is added**: any technology with a high C-rate relative to its round-trip efficiency is a candidate for the same exploit. `util/analyze_charge_discharge_exclusivity.m` (new `analyze_*` function, same house style as `analyze_losses`/`analyze_curtailment`) reports and plots this per-technology; called from `run_seq_lin_loop_ess.m` whenever `~opts.cha_dis_bin_activate`.

**A second, separate issue in the same penalty term: large `cha_dis_penalty_eps` can pick the wrong (lossy) technology, not just a C-rate exploit.** The penalty `costPenalty = penalty_unit_cost * sum(sum(B_plus + B_minus)) / T` is *added to* the throughput-loss cost `costBESSLoss` (`opts.throughput_penalty`), not a scaled copy of it — and their combined dependence on a technology's round-trip efficiency `rho_j = eta_ch(j)*eta_dis(j)` flips sign once `cha_dis_penalty_eps` crosses a threshold (derived in `docs/relaxed-penalty-substandard-tech-selection.md`: `eps* = c_sp * 8760 * life_span / min(cE,cS)`, independent of horizon length — currently `≈197` at live prices, vs. the `1e+2` default which sits just below it). Above that threshold, the *lossy* technology becomes cheaper, not the efficient one. **A `charge_referred` penalty variant (dividing the discharge term by `eta_ch(j)*eta_dis(j)` before summing) was implemented and verified to fix this (2026-09-28, `experiments/test_charge_referred_penalty.m`), then reverted at user request (2026-09-29) back to the single plain form** — `solve_ess_milp.m` now only has `costPenalty = penalty_unit_cost * sum(sum(B_plus + B_minus)) / T`, no `cha_dis_penalty_form` config branch. The derivation and verification data are preserved in `docs/relaxed-penalty-substandard-tech-selection.md` for reference. **Practical implication of the revert**: keep `cha_dis_penalty_eps` below the ~197 threshold (current default `1e+2` is), or technology selection is not protected against this bias at high eps.

**`analyze_charge_discharge_exclusivity.m` reports two violation metrics, not one, because they answer different questions**: `phantom_pct = sum(B_exc)/sum(B_plus+B_minus)` (existing) is the phantom share of that node's own total dispatched *energy* over the whole horizon — not comparable across nodes, since a low-throughput node makes a small violation look huge (%) and a high-throughput node hides a real one. The added `max_rating_frac`/`n_exceed_k` metric is `B_exc(t) / (c_rate(j) * E_nom(n,j))` per timestep — the phantom power as a fraction of that (node, tech) pair's own individual charge/discharge cap, bounded in `[0,1]` by construction since `B_plus`/`B_minus` are each already box-constrained to `c_rate*E_nom` (`solve_ess_milp.m:183-184`). **Not `kP*S_conv`** — that box (`solve_ess_milp.m:197-204`) only bounds the *net* dispatch `B_bat_var = B_plus-B_minus`, so it never caps `B_plus`/`B_minus` individually; using it as the denominator was tried first and produced fractions over 100%, which is how the mistake was caught. `rating_thresh` (default `0.01` = 1%) sets how many timesteps count as "exceeding" — sourced from `cfg.solver.cha_dis_rating_thresh` (`util/sizing_cfg.json`, same `solver` block as `cha_dis_penalty_eps`) when `cfg` is passed, overridable via the function's 4th argument, falling back to `0.01` hardcoded only for cfg-less calls. On a `LV_Grid_230` relaxed-formulation smoke test the two metrics told visibly different stories for the same violation: `phantom_pct=14.8%` (looks mild, diluted by a whole day of clean dispatch) vs. `max_rating_frac=83.8%` (looks severe — at its worst single timestep that node charged and discharged at 84% of its own max rate simultaneously). Both numbers are correct; they're just answering "how much of my energy was wasted" vs. "how close did my worst moment get to a full-power contradiction."

**`D` (synthetic-day count) and `Ts_h` (time-step) are config-driven, not hardcoded**: `build_temporal_profiles.m`'s WIP demand generator (`generate_nodal_scenarios_4`, GMM-based, explicitly a stand-in for the eventual load-profile source) once took a hardcoded `D` and a hardcoded `96` steps/day. Both now come from `util/sizing_cfg.json`'s `"horizon"` block: `days` (= `D`) and `Ts_h`. `load_ess_selection_config` derives `cfg.horizon.steps_per_day = 24/Ts_h`, `preprocess_network` reads `D = cfg.horizon.days` (positional `D` arg still overrides, as the `experiments/` scripts use) and passes `steps_per_day` down through `linear_grid_model(grid, horizon, D, steps_per_day)` → `build_temporal_profiles(grid, horizon, D, steps_per_day)`. `build_temporal_profiles` takes the *native* steps/day from the data itself (`size(nodal_injections_D, 3)`), uses it for the `D`-day replication, and **errors** if it disagrees with `steps_per_day` — i.e. `Ts_h` is only free to the extent the input data supports it (15-min data → `Ts_h` must be `0.25`; a real resolution change needs `PV_prof_15mins.mat` / `EV_uncontrolled_profile` / the load generator resampled first). `Ts_h` is the single source of truth for the per-step duration everywhere: `solve_ess_milp.m`, `build_network_result.m` (which also stamps `out.meta.{Ts_h,horizon_days,steps_per_day}`), and the `analyze_*` diagnostics all read it (from `out.meta.Ts_h` when working off a reloaded `.mat`, else `cfg`), and `load_ess_selection_config` mirrors it to `cfg.solver.Ts_h` for any missed reader. This makes `T = D * steps_per_day` horizons (e.g. `days=365` for a full year) reachable from JSON alone. **Caveat discovered during a `D=1..7` sweep**: `D` values are *not* nested/reproducible against each other — `generate_nodal_scenarios_4.m` fits a GMM that's flagged as not converging in 100 EM iterations. **Correction (2026-09-15, superseding the original note below)**: `fitgmdist` itself is NOT inherently non-deterministic — directly verified (`experiments/test_load_profile_determinism.m`, check D) that fitting the identical data twice with the ambient rng reset identically before each fit gives byte-identical parameters (diff=0). The real cause of non-nested `D` values is the residual-sampling loop's structure: `generate_nodal_scenarios_4.m` draws `for i=1:n_nodes, for j=1:D, random(cluster_gmm{...})`, i.e. `D` consecutive draws per node before moving to the next node. Only node 1's first draw is shared between a `D=1` and a `D=7` call from the same starting rng state; every subsequent node's draws are offset by a different number of prior draws depending on `D`, so they diverge from node 2 onward. This is expected behavior of sequential stream sampling, not a defect — but it does mean different `D` values on the same network are distinct demand realizations, not a clean horizon-length sweep, exactly as the original note concluded (just for a different reason than stated).
~~thread-level floating-point non-associativity in `fitgmdist` makes the fit itself non-deterministic run-to-run, even under identical RNG seeding (verified directly: reseeding `rng(1234+net_num)` before each call did *not* restore nesting)~~ — **retracted**, see correction above. Separately, note that `generate_nodal_scenarios_4.m`'s `network_id`/`seed` argument only deterministically controls `nodal_clusters` (`rng(seed,'twister') -> randsample -> rng(prev)` immediately restores the caller's ambient rng state) — the GMM fit and every residual draw run on whatever the ambient global rng state is at call time, so a call is reproducible only if the caller's ambient rng state is itself controlled/identical at entry (see the corrected docstring in `util/generate_load_profile.m`). This codebase's actual usage is safe: `solve_network_tech_selection.m` calls `rng(1234+net_num)` once per network before anything else runs, and `build_temporal_profiles.m` always generates demand first (before PV/EV), so demand is reproducible run-to-run for a fixed network regardless of which PV/EV/tech options are toggled.

**Demand/PV/EV profile generation is now three separate, config-driven generators, not inline code in `build_temporal_profiles.m`**: `build_temporal_profiles.m` is a thin orchestrator that calls `generate_load_profile.m` (demand, still backed by `generate_nodal_scenarios_4`'s GMM sampler), `load_pv_profile.m` (PV, reads `util/pv_profiles_year.mat`), and `generate_ev_profile.m` (EV, backed by `EV_uncontrolled_profile`), then slices/reshapes all three the same way via `slice_day_contiguous_pu.m`. Each generator takes its own sub-struct — `profile_params.demand`/`.pv`/`.ev` — sourced from `sizing_cfg.json`'s `demand_profile`/`pv_profile`/`ev_profile` blocks via `preprocess_network.m`; unset fields fall back to each generator's own defaults via `set_default.m`. Every sub-struct accepts `.enabled` (default `true`) — `false` zeros out that stream while still returning the correct native resolution (no wasted GMM fit / file read). `load_pv_profile.m` additionally accepts `.series` (`"clearsky"` | `"measured"`, both from `pv_profiles_year.mat`, generated via pvlib — see the `.scale` note below for provenance) and `.season`. **PV day-selection depends on `D`**: `D==1` → single representative day, the real day with minimum RMSE from the season's mean-shape day (`select_representative_day.m`); `D==7` or `D==30` → representative week/month via the Finkelstein-Schafer statistic on the daily-energy distribution (`select_representative_window.m`, cyclic at the winter Dec→Jan boundary); `D==Ndays` (365) → full year, calendar order (`.season` must be `"all"`); otherwise → legacy first-`D`-consecutive-calendar-days fallback. In every case the selected day(s)' data is used unmodified — representativeness only picks *which* real day(s), never averages/smooths. `plot_temporal_profiles.m` (kept separate so `build_temporal_profiles.m` has no plotting side effects) is the standalone diagnostic for all three streams.

**`pv_profile.scale`** (`sizing_cfg.json`, default `1`): a multiplicative factor on `load_pv_profile.m`'s returned kW stream, applied after the `node_peak_kw` scaling — e.g. `1.5` for a +50% PV-oversizing sensitivity run. Verified to scale output linearly (`experiments/test_load_profile_determinism.m`-adjacent smoke test, not committed). **`pv_profiles_year.mat`'s provenance**: pvlib was used to convert irradiance into normalized DC power (haydavies transposition, ineichen clearsky, faiman cell-temp models) for two weather scenarios — `pv_norm_clearsky` (idealized, no clouds) and `pv_norm_measured` (PVGIS-TMY typical-year weather) — both cached per-unit of installed peak DC power. The two series are **not** interchangeable for results: on `LV_Grid_230` this session, `measured`'s representative day showed zero PV-driven violations while `clearsky`'s showed a real self-export overcurrent — `clearsky` is the safer default for a "PV can cause violations" claim; see `docs/tech-profile-ablation-study.md`.

**EV is included in the operating point (`linear_grid_model.m`), same as PV**: the per-timestep injection is `to_all_nodes_D*demand + to_all_nodes_PV*PV + to_all_nodes_EV*EV` — EV was not always in this sum; verify any code reading `gm.lm.P0`/`Q0`/`Vmag0` etc. was generated after this was wired in if working from an old saved `.mat`. Relies on the same **PV/EV-nodes-are-a-subset-of-demand-nodes** property documented for PV curtailment above (verified across the tested portfolio) — this is what lets EV/PV injections survive the N→Nd projection into `sens.P0` without threading new arguments through `OPF_verification.m` (which only takes an explicit PV argument, for curtailment). A network with PV-only or EV-only nodes (no demand there) would need that stream passed explicitly, same as PV curtailment already is.

**Fixed bug: EV charging demand didn't scale with the number of EVs at a node**: `build_temporal_profiles.m` used to call `generate_ev_profile(sum(nodes_with_EV), ...)` — the count of EV-*hosting nodes*, not the count of vehicles. `generate_ev_profile.m` then drew exactly one `EV_uncontrolled_profile` column (one simulated vehicle) per node and mapped it 1:1, so a node with `nodal_N_EV=3` got the identical single-vehicle demand as a node with `nodal_N_EV=1` — the actual count (`grid.nodal_N_EV`, a real per-node vehicle count from `allocate_PV_EV_SFOE.m`'s discrete largest-remainder allocation) was read only as `>0` and never used again anywhere in the codebase. Fixed by passing `grid.nodal_N_EV(nodes_with_EV)` (`build_temporal_profiles.m:99-101`) instead of the scalar node count; `generate_ev_profile.m` now draws `sum(node_ev_counts)` individual vehicle profiles (one `EV_uncontrolled_profile` call, so all vehicles share one draw of the arrival-time distribution) and sums each node's own vehicles into that node's row before tiling across `D` days.

**Demand's and EV's rng seed offsets are config-driven, and must stay two separate fields**: `build_temporal_profiles.m` derives each stream's local seed as `str2double(grid.net_id) + <stream's own seed_offset>` — now sourced from `demand_profile.seed_offset` (default `1236`) and `ev_profile.seed_offset` (default `5678`) in `sizing_cfg.json`, each independently overridable. **They must never be set to the same value**: both `generate_load_profile`'s `nodal_clusters` draw and `EV_uncontrolled_profile`'s arrival-time draw use the same save/seed/restore pattern (`prev_rng=rng; rng(seed,'twister'); <draws>; rng(prev_rng)`), so an identical seed would reset both to the same starting point in the rng sequence — demand's cluster assignment and EV's arrival times would stop being independent draws, and there would be no way to vary one (e.g. for a future EV-arrival-time Monte Carlo, holding demand fixed) without also reshuffling the other. Verified: same config twice reproduces identical demand and EV (regression-safe); changing only `ev_profile.seed_offset` changes EV but leaves demand byte-identical, and vice versa for `demand_profile.seed_offset`; full pipeline still solves.

**`ev_profile.force_single_ev_per_node` (default `false`) is a test/comparison-only flag, not for real results**: set `true` to make `generate_ev_profile.m` treat every EV-hosting node as if it had exactly 1 EV, regardless of its real `grid.nodal_N_EV` count — i.e. it exactly reproduces this repo's pre-fix behavior (the "EV charging demand didn't scale with the number of EVs" bug above), for A/B comparison against the corrected per-count behavior. Verified: flag off scales exactly with count (a 3-EV node peaks at 3x a 1-EV node's, a 5-EV node at 5x); flag on gives identical peaks across nodes regardless of count, byte-identical to calling with every node forced to count 1; the default (field omitted) matches `false` explicitly; full pipeline still solves.

**`ev_profile.synchronized_arrivals` (default `false`) is a scenario flag for a worst-case "all EVs at this node plug in at once" stress test**: normally (`false`) each vehicle at a node draws its own independent arrival time (staggered); `true` draws one arrival per *node* instead and gives every vehicle at that node the same arrival, turning a multi-EV node's profile from a staircase into a single flat block of height `count*charger_kw/3` for the full 4h window. Purpose: isolate whether concentrating a node's EV load into one simultaneous spike (vs. today's realistic staggered arrivals) changes technology selection — directly relevant to the C-rate/power-density sensitivity investigated in this session. Same total daily energy either way; only the timing/peakiness changes. Verified: default (field omitted) matches explicit `false`; a 1-EV node is byte-identical either way (nothing to synchronize); on a 3-EV test node with a tight arrival spread (σ=0.6h vs. 4h charging duration), peak power and total energy happened to come out identical between the two modes (the staggered arrivals already fully overlapped by chance for that seed) — confirmed this is not a silent no-op by checking the whole-day timeseries directly: they differ (OFF ran nonzero for 18 steps, ON for 16 — ON's instant on/off vs. OFF's gradual ramp-up/ramp-down). Full pipeline still solves.

A second, stronger flag, `ev_profile.synchronize_across_nodes` (default `false`, only meaningful when `synchronized_arrivals=true`), forces **every EV in the whole network** — not just within one node — onto the same single arrival draw (`EV_uncontrolled_profile(1, ...)` broadcast to every node, instead of one draw per node). Verified: all nodes share an identical onset/offset window, each node's peak is exactly `count*charger_kw/3`, and `synchronize_across_nodes=false` (default) reproduces the original per-node-sync behavior exactly.

**Finding from this investigation (2026-09-29): EV arrival timing is not what drives NaIon vs. LiIon selection on `LV_Grid_230`, at any level of synchronization tried.** After the count/phase/seed fixes above, this network's technology selection stopped needing NaIon at `charger_kw=11`. A screen of 5000 EV `seed_offset` values (`experiments/screen_crate_need.m`, scoring each node's peak/average power ratio without running the MILP) found the "natural" (staggered) arrival distribution already overlaps almost fully regardless of seed (median ratio 6.0 out of a theoretical max ~6, essentially no spread) — so seed search has no real leverage here. Verified directly: neither the best-of-5000 staggered seed, nor per-node synchronization, nor full network-wide synchronization (all 11 EVs at once, the most extreme case testable) brought NaIon back — all three gave LiIon at every installed node, only the total cost rose (12.74 → 32.28 → 36.10 kCHF as the stress increased). The determining factor is most likely the corrected power *magnitude* itself (from the ÷3 phase and per-node-count fixes), not EV timing/clustering — worth checking `charger_kw` between the known `11` (LiIon suffices) and `22` (infeasible) values, or a different network, before concluding NaIon is never needed post-fix.

**EV charger rating is config-driven, not hardcoded**: `sizing_cfg.json`'s `ev_profile` block has `charger_kw` (default `3.7`, matching the previous hardcoded value), threaded through `generate_ev_profile.m` into `EV_uncontrolled_profile.m`'s `charger_kw` argument (replacing the old fixed `P_ev=3.7`). Lets a sensitivity run test higher-power (e.g. 11/22 kW three-phase) chargers without touching code. Verified: omitting the field reproduces the exact old behavior (`isequal` on the output), a different value scales the resulting single-phase-equivalent power exactly proportionally (`11kW -> 11/3.7x` the default), and a full pipeline solve at the default value reproduces the same 12.74 kCHF result as before this change (a pure no-op at default). Still assumes the rating is a 3-phase-total quantity (the ÷3 below applies unconditionally) — a genuinely single-phase-only charger rating is a separate, not-yet-modeled case, deferred as future work.

**Fixed bug: EV power wasn't converted to the single-phase-equivalent convention (was 3x too large)**: `get_grid_SFOE.m:132-134` divides demand and PV by 3 (their SFOE-sourced figures are real 3-phase totals; dividing gives the per-phase value this repo's `n_of_phases=1` single-phase-equivalent load flow uses) before those peaks ever reach their profile generators. **Fixed bug: EV arrival times had no seed, so changing vehicle count reshuffled every arrival, not just the added vehicles'**: `EV_uncontrolled_profile.m`'s rejection-sampling loop drew from whatever the ambient global rng state happened to be — no seed of its own (unlike demand, which at least has a `net_id`-derived `seed` for its `nodal_clusters`, per the `generate_nodal_scenarios_4.m` note above). This meant e.g. the EV-count fix above (going from 9 to 11 total draws on `LV_Grid_230`) changed every one of the 9 pre-existing arrival times too, not just the 2 new ones — confounding any before/after comparison, and leaving the whole EV realization un-reproducible and unable to vary count and randomness independently. Fixed: `EV_uncontrolled_profile.m` takes an optional `seed`, applying the same save/seed/restore pattern as `nodal_clusters` (`prev_rng=rng; rng(seed,'twister'); <draws>; rng(prev_rng)`); `generate_ev_profile.m` forwards it; `build_temporal_profiles.m` computes `ev_seed = str2double(grid.net_id) + 5678` (a different offset from demand's `+1236`, so the two streams don't share a stream position) and passes it through. Verified: same seed + same count → bit-identical arrivals; same seed, count 9 vs 11 → the first 9 arrivals are unchanged (only the 2 new vehicles' arrivals are new); same seed regardless of the ambient rng state beforehand → identical arrivals (true reproducibility, not just "safe under this pipeline's fixed call order" like demand).

**Load-flow convergence is tracked and hard-gated, not silently trusted**: `loadflow_FPIs.m`'s signature is extended to `[Vk1, I, S, converged, num_iter] = loadflow_FPIs(...)` — pure instrumentation (checks `max(abs(Vk1-Vk)) < 1e-5` each of the fixed 20 iterations; zero change to `Vk1`/`I`/`S` themselves). `summarize_lf_convergence.m` rolls per-timestep `converged`/`num_iter` into `.all_converged .n_converged .n_total .pct_converged .failed_idx .max_iter .mean_iter`, tracked at three call sites: `linear_grid_model.m` (base operating point, → `gm.lm.lf_converged/lf_num_iter/lf_summary`), `re_linearization.m` (re-linearized operating point, same fields — only exercised when `MAX_LIN_ITER>1`), and `grid/OPF_verification.m` (solved-dispatch "ground truth" check, consumed by `run_seq_lin_loop_ess.m` → `out.diagnostics.lf_converged/lf_num_iter/lf_summary`). **Hard stop (temporary, pending a real `loadflow_FPIs` damping/robustness fix)**: any of the three sites throws (`linear_grid_model:lfNotConverged` / `re_linearization:lfNotConverged` / `run_seq_lin_loop_ess:lfNotConverged`) rather than warns if `~lf_summary.all_converged` — a non-converged FPI feeds garbage sensitivities/ground-truth downstream otherwise. This needs zero new plumbing: `run_ess_selection_portfolio.m`'s existing per-network `try`/`catch` already routes any uncaught error to `out_dir_error/<net_num>.mat` and continues the portfolio loop, so the hard stop only ever kills the one offending network. Convergence is load-dependent, not a network-configuration property — e.g. `LV_Grid_86888` converges 100% under demand+PV but fails ~17% of timesteps (exactly the EV charging window) once EV is added; `loadflow_FPIs_convergance.m` (damped, adaptive-iteration-cap, voltage-floor-guarded) is the known fix candidate but is **not wired into the active pipeline** — zero callers, and incompatible as-is with the `YLLi`-reuse perf optimization (rebuilds `YLL \ Iinj` fresh every iteration). `analyze_loadflow_convergence.m` reports/plots both stages' convergence from a saved `out` (PASS/WARN console lines + optional per-timestep iteration-count figure); called from `run_seq_lin_loop_ess.m` when `enable_plots`.

**Fixed: `costL`/`costCurt`/`costBESSLoss`'s `* 365 * 15` annualization no longer double-counts at full-year scale**: the multiplier scales a simulated period's summed loss/curtailment energy up to an annual/lifetime basis to match the one-time capex terms (`costE`/`costS`/`costI`) — correct as a bare `*365*15` only when the horizon is exactly one simulated day (`D=1`); at `D=365` the horizon *is* the real year already, so applying `*365` again would inflate a real year of losses into a fictional 365 years. Fixed (`solve_ess_milp.m:296-316`) by dividing by `days_simulated = T*Ts/24` first: `costL = cL*Ts*sum(P_sloss)/days_simulated*365*15` (same pattern for `costCurt`, `costBESSLoss`). At `D=1`, `days_simulated=1` and the formula reduces to the original `*365*15` unchanged; at `D=365`, `days_simulated=365` and the `365/365` cancels, leaving just the `*15` lifetime factor — no double-counting. This is algebraically identical to the `Ψ = 8760*L/(T*Δt)` annualization factor derived for the charge/discharge penalty crossover (`docs/relaxed-penalty-substandard-tech-selection.md`): `365*15/days_simulated = 365*15*24/(T*Ts) = 8760*15/(T*Ts) = 8760*L/(T*Δt) = Ψ`, so `costL = cL*Ts*sum(P_sloss)*Ψ` — same Ψ, applied directly to the physical loss-cost term rather than folded into a per-unit spot price the way the penalty term uses it. `life_span` (`15`) is still hardcoded rather than pulled from `technology_cfg.json` per-tech, per the pre-existing note in "Curtailment/loss cost units" below — that part is unchanged by this fix.

**`flags.lossless_bess` (default `false`) models a 100%-round-trip-efficient BESS to get a lower-bound estimate of required `E_nom`/`S_conv`**: at `eta_ch=eta_dis=1` there is no round-trip loss, so `B_plus`/`B_minus` (two independent nonneg variables, needed only to let charging and discharging lose energy at different rates) collapse into one signed net-power variable `B_bat` — and with a single real variable, there is no "simultaneous charge and discharge" to guard against, so the whole `ct` binary / relaxed-penalty apparatus becomes unnecessary **by construction**, not just switched off. `solve_ess_milp.m` branches on this flag (`lossless_bess = isfield(opts,'lossless_bess') && opts.lossless_bess`, read once near the top): `variable B_bat(T*Nd,J)` replaces the `B_plus`/`B_minus`/`dB_plus`/`dB_minus` quartet; the SOE recursion drops the `eta_ch`/`eta_dis` terms entirely (`SOE(t) == SOE(t-1) + Ts*B_bat(t)`); the C-rate constraint becomes one box (`-c_rate*E_nom <= B_bat <= c_rate*E_nom`) instead of two one-sided bounds; `ct` is never declared and the Big-M exclusivity block is skipped regardless of `cha_dis_bin_activate`; `costPenalty` and `costBESSLoss` are both forced to `0` regardless of `cha_dis_penalty_eps`/`throughput_penalty`'s config values (there's no loss and no exclusivity to price). `cfg.tech.eta_ch`/`eta_dis` are not read in this mode at all. **Zero ripple into any downstream consumer**: after `cvx_end`, `sol.B_plus`/`sol.B_minus` are synthesized from the solved `B_bat` (`max(B_bat,0)`/`max(-B_bat,0)`) before being packed — since `run_seq_lin_loop_ess.m`, `build_network_result.m`, `analyze_charge_discharge_exclusivity.m`, and `analyze_losses.m` all only ever read `sol.B_plus`/`sol.B_minus` (never a raw CVX variable), every one of them works completely unchanged; warm-starting also needs no new field, since `prev.B_plus_prev - prev.B_minus_prev` reconstructs `B_bat_prev` exactly (the synthesized fields round-trip cleanly because they're disjoint by construction — one of each pair is always exactly 0). Threaded into `opts.lossless_bess` by `solve_network_tech_selection.m` alongside the other flags. **Verified**: a 7-day smoke test (`LV_Grid_101`, LiIon, `eta=1`) solved cleanly with `Penalty cost=0.000000` and `Eloss cost=0.000000` (forced, not just near-zero), and the independent `analyze_charge_discharge_exclusivity` check confirmed 0% phantom throughput at every node — the structural guarantee holds empirically, not just in theory. A 1-day (`D=1`) smoke test reported `Infeasible` for both this new formulation *and* the unmodified original two-variable formulation under the identical inputs (same `eta=1`, same demand draw) — ruling out a bug in this feature and instead pointing at `D=1`'s single-GMM-residual-draw demand realization being an unlucky/atypical outlier for this network (see the `D`/`Ts_h` note's discussion of `generate_nodal_scenarios_4`'s per-day sampling), not something this flag caused.

**`analyze_losses.m`'s active-power loss panel must use `out.injections.P_sloss`, not recompute it**: `P_aggr`/`dP` (and hence `P_aggr_upd`) are summed only over `out.injections.P0_mat`/`delta_P` — demand-node (`Nd`-space) quantities. PV curtailment lives in `Npv`-space, which may not even overlap `Nd`, so a manual `P_loss_upd = P_s_upd + P_aggr_upd` recomputation is blind to curtailed power entirely: it misattributes the curtailed PV as "loss" (the gap in Nd-space bookkeeping), producing a `P_loss_upd` spike that tracks curtailment, not real network losses, whenever `opts.curtailment_activate`. Fixed by using the solver's own `out.injections.P_sloss` (which already includes the `pv_loss_adj` term) for `P_loss_upd` when present, falling back to the old recomputation only for pre-curtailment saved results that lack the field. The reactive panel (`Q_loss_upd`) doesn't need the same fix — curtailment changes active power only, so `Q_aggr` needs no analogous adjustment, and `Q_s_upd = imag(Sl_Q)` already reflects curtailment's P→Q cross-term correctly.

**Curtailment/loss cost units (`costL`, `costCurt`)**: `P_sloss` and `P_curt` are *power* variables (one value per timestep); `cfg.economics.cL`/`cCurt` are CHF/kWh *energy* prices. `solve_ess_milp.m` bridges the two by multiplying through `Ts` (0.25 h) before applying the price — `costL = cL * Ts * sum(P_sloss)`, same for `costCurt` — matching the same power→energy conversion already used for `SOE` evolution and for `out.summary.curtailed_energy_pu = sum(P_curt) * Ts`. Both `costL` and `costCurt` additionally multiply by `365 * 15` (days/year × technology `life_span`, years) to annualize the single simulated day's operating cost up to the same lifetime basis as the one-time capex terms (`costE`/`costS`/`costI`); the `15` is currently hardcoded rather than pulled from `technology_cfg.json`'s per-tech `life_span`. The whole objective is then divided by `1000` in `solve_ess_milp.m`'s `minimize(...)` call (a uniform scalar, purely for display as "thousand Francs" — has no effect on which solution is optimal); `sol.costs.*`/`out.costs.*` are *not* divided by this, so they stay in raw CHF.

**pu → real-CHF cost coefficients (`cE`, `cS`, `cI`, `cL`, `cCurt`)**: `E_nom_pu`, `S_conv_pu`, `P_sloss_pu`, `P_curt_pu` all live on the same per-unit base as every other power/energy quantity in this model: 1 pu = `bp * ph` real kWh/kW, where `bp = Sb/1000 = 100` (single-phase base; `Sb=100,000` in `general_config.json`) and `ph = 3` (phase count) — traceable end-to-end through `grid/get_grid_SFOE.m:132` (`nodal_demand_all/3`, converting a real 3-phase total to the per-phase value the `n_of_phases=1` single-phase-equivalent load flow uses) and `util/preprocess_network.m:74-75` (`T_rat_kVA/3`, explicitly commented "3-phase kVA... per-phase pu"). `load_ess_selection_config.m` therefore scales the CHF/kWh or CHF/kW real-world prices *up* by `bp*ph = 300` — `cfg.tech.cE = (cE_kWh/bph)*ph` where `bph = 1/bp` (so `X/bph == X*bp`) — so that e.g. `costE = E_nom_pu * cE` equals real CHF directly, not just a value proportional to it. `cfg.tech.cI` (the technology's fixed installation cost) is the one exception: `I` is a dimensionless 0/1 decision (not a pu quantity that represents 300 real units), so it's left as `cI_fixed` with **no** `bp`/`ph` scaling at all. **Historical bug (now fixed)**: an earlier version divided all five coefficients (including `cI`) by `bp` uniformly, which — because `I` doesn't carry the same 300× compression as the other four decision variables — made `costI` ~300× overweighted relative to `costE`/`costS`/`costL`/`costCurt` within the objective. This biased the solver against installing batteries and toward curtailment even when curtailment was the objectively more expensive real-world choice (confirmed by comparing `cvx_optval` against hand-computed real CHF for matching scenarios). If `cI` is ever touched again, remember it must **not** get the `bp*ph` treatment the other four coefficients need.

**Curtailment reporting**: `analyze_curtailment(out, cfg)` (gated by `opts.curtailment_activate`, called from `run_seq_lin_loop_ess.m` alongside `analyze_tech_selection`/`analyze_losses`) reports the objective cost breakdown (`out.costs.{E,S,I,L,Curt,total}`), per-PV-node curtailed energy and available-vs-delivered time series (derived from `out.gm.injectinos_PV_pu` — the pre-curtailment availability — and `out.injections.P_curt`), and slack active power / loss proxy (`out.injections.P_sloss`) before vs. after solving. The before/after slack comparison nets in BESS dispatch *and* curtailment together — the two aren't decomposed, since isolating curtailment's marginal effect on `vmag`/`P_sl` would require re-deriving the PV sensitivity terms (`sens.dVmagdP_PV` etc.), which aren't persisted in `out`.

Call it after loading a solved `.mat`: `analyze_tech_selection(out, cfg)`.

**Voltage/current reporting**: `analyze_voltage_current(out)` plots nodal voltages (Fig 1) and line currents in pu of ampacity (Fig 2), each showing initial operating point / solved linear model / solved nonlinear load flow, plus error and before-vs-after-shift subplots. (That `[0.001, 200]` range is `solver.VMAG_LB/VMAG_UB`, a sanity check for broken networks, **not** the operational voltage limits; those are `solver.V_MIN/V_MAX` below.)

**Base-operating-point violation report (`util/report_violations.m`)**: called from `solve_network_tech_selection.m` right after `check_voltage_guard` passes, on the no-ESS operating point (`gm.lm.Vmag0`/`Imag0`), i.e. the violations storage is being asked to fix. Prints to console and to the run log (`run_opts.log_fid`). One line per violating node/direction and per overloaded line, summarised over all `T` steps and sorted most severe first: node ids are **topology ids** (`N`-space row `k` → node `k+1`, same `+1` slack shift as `out.sizing.demand_node_id`) plus `graph_data.node_names`; lines print as `node <from> -> node <to>` from `grid.N1N2Y(:,1:2)` (already topology numbering), with current and ampacity in **amperes** (`|I_pu| * grid.basecurrent` vs `grid.ampacities`, which are stored in A), and the transformer branch flagged via `graph_data.tr_branch_idx`. A node that goes OVER at some steps and UNDER at others gets two entries; this shows directly whether a node's required correction is one-signed, which is what matters for the terminal-SOE infeasibility discussion. Step-range lists are capped at 6 ranges for long horizons. Takes plain arrays, so it can be rerun on the solved load flow (`out.grid.V_lf`/`I_lf`, reshaped to `[N x T]`/`[L x T]`) for a before/after comparison; that second call is not wired in yet. Verified on `LV_Grid_101` (shapes: 77 nodes → topology 2..78, 77 lines) and on a synthetic case covering UNDER, dual-direction nodes, the transformer flag and the range cap.

**`flags.save_opf_output` (default `true`) gates whether a solved network's full result gets written to disk**: `run_ess_selection_portfolio.m`'s `'solved'` case used to call `save(fname_solved, '-struct', 'out')` unconditionally — the only way to avoid it was to not run the network at all. `false` skips that write (the dominant cost is `out.gm`, the largest field) while everything else is unaffected: console/log reporting, `analyze_*` diagnostics (`enable_plots`), and `all_dispatch_logs.mat` bookkeeping all still run off the in-memory `result`/`out`, only the per-network `.mat` never gets written. The run log records which happened: `SOLVED ... (not saved: save_opf_output=false)` vs. the normal line with no suffix. Verified directly: with the flag `false`, an existing `out_dir_solved/<net>.mat`'s mtime is provably untouched by a fresh solve of the same network. Meant for a fast sweep (many networks/seeds/configs) where only the log-line summary (E/S/cost/errors) is needed, not the full reloadable result. **Interacts with `run_opts.skip_solved`**: that flag's re-run-avoidance check is `isfile(fname_solved)`, so with `save_opf_output=false` the file never exists and every sweep iteration re-solves regardless of `skip_solved` — expected, not a bug, but worth knowing if combining the two. `thresh`/`subopt`/`error` statuses are unaffected by this flag — those are small status stubs (not "the OPF output"), not gated.

**Gurobi parameters come from `cfg.solver.gurobi` (`util/sizing_cfg.json`, `solver` block)**: `solve_ess_milp.m` passes every field of that struct (`MIPGap`, `FeasibilityTol`, `OptimalityTol`, `BarConvTol`, `BarQCPConvTol`, and any other valid Gurobi parameter such as `IntFeasTol` or `TimeLimit`) via `cvx_solver_settings(...)` right after `cvx_begin`, so they are local to that model. An absent or empty block means Gurobi's own defaults (MIPGap 1e-4, FeasibilityTol/OptimalityTol 1e-6). The committed values reproduce the old CVX-shim hardcodes (MIPGap 1e-6, tolerances 1.49e-8). **This depends on the CVX install, not this repo**: `cvx_gurobi.m` (`<CVX>/shims/`) must call `cvx_run_solver(@gurobi, prob, params, 'res', settings, 2)` — the previous index `3` (in this install) made every custom setting fail with an empty `gurobi()` error — and its hardcoded `params.MIPGap/FeasibilityTol/...` lines must stay commented out (settings override them anyway, but commented-out keeps this file the single source of truth). Settings only reach Gurobi if set *after* `cvx_solver gurobi` runs (they are stored for the currently active solver), which is why they sit inside the model. Check the Gurobi log's "Set parameter" lines to confirm what was actually received.

**Voltage convergence threshold**: `VOLT_CONV_THRESH = 0.01` pu. If `max|vmag_lin - V_lf| < 0.01`, the sequential linearization exits early.

**`horizon`**: a vector of timestep indices into the native (15-min, 96-step) day, e.g. `1:96` (full day) or `1:32` for a shorter debug window; `[]` means the full native day. Still a `main.m` knob (`D`/`Ts_h` moved to `sizing_cfg.json` — see the `D`/`Ts_h` note above). Consumed by `build_temporal_profiles`/`linear_grid_model`/`preprocess_network`. The underlying cluster/arrival-time statistics (`generate_nodal_scenarios_4`, `EV_uncontrolled_profile`, `PV_prof_15mins.mat`) are all keyed to a full day, so `build_temporal_profiles` always builds the full native-day profiles first and then slices rows down to `horizon` — it does not regenerate statistics for a shorter day. `grid/OPF_verification.m` derives `T` from `size(Injections, 1)` (previously hardcoded to 96), so any `T` produced by a given `horizon` verifies correctly. **WIP note**: demand comes from `generate_nodal_scenarios_4` (a GMM-based synthetic-day sampler), replicated over `D = cfg.horizon.days` days, so `profiles.T = numel(horizon)*D` — a `horizon=[]` run with `days=1` gives `T = 96`; `days=365` gives `T = 35040`. This is a testing stand-in for the eventual real load-profile source. **Known pre-existing inconsistency**: for `horizon ≠ full day`, demand is replicated to `steps_per_day*D` rows but PV/EV are sliced to `numel(horizon)` rows only (one day, un-replicated) while `profiles.T = numel(horizon)*D` — harmless for the default `horizon=[]` (where `numel(horizon)==steps_per_day`), not yet reconciled for partial horizons.

**`demand_profile.allow_ts_downsample` (default `false`) is a workaround for running at a coarser `Ts_h` than the native 15-min demand data, without touching the GMM data source**: setting `horizon.Ts_h` (e.g. `1` for hourly) to anything other than `0.25` normally hits `build_temporal_profiles`'s `check_steps_per_day` guard and errors (native 96 steps/day vs. the configured `steps_per_day`) — this flag, checked only for the demand stream, instead **block-averages** every `S_native/steps_per_day` consecutive 15-min samples into one coarser step (`reshape`+`mean`, not decimation — deliberately chosen over picking every Nth sample so total daily energy is conserved exactly; a decimated sample would make peak power arbitrary depending on whether a spike happens to land on a kept sample, which matters a lot for this model's peak/C-rate-driven tech selection). Only integer-factor **downsampling** is supported (errors if `steps_per_day` doesn't divide evenly into the native count, or if it would be upsampling). **Trade-off to know**: block-averaging smooths spikes, so a coarser-`Ts_h` run understates the true 15-min peak power — results from an `allow_ts_downsample` run are not directly comparable to a native 15-min run for anything peak-driven (C-rate binding, tech selection). PV/EV are untouched by this flag — "for the loads" only, per user request; a genuine PV/EV resample is deferred. To actually make a mismatched `Ts_h` usable end-to-end, `check_steps_per_day` was also changed to **skip the check entirely for PV/EV when that stream's own `.enabled` is `false`** — a disabled stream returns an all-zero array regardless of its native resolution (`load_pv_profile.m`/`generate_ev_profile.m`), so which native indices `horizon` happens to slice out of it doesn't matter; without this, PV/EV's own native-96 mismatch would still block the run even with EV/PV switched off. Verified end-to-end: `Ts_h=1` with `demand_profile.allow_ts_downsample=true`, `pv_profile.enabled=false`, `ev_profile.enabled=false` on `LV_Grid_101` solves cleanly (`T=24`, 100% load-flow convergence at both stages, no `tsMismatch` error) — result had zero ESS installed, expected since the smoothed hourly demand alone (no PV/EV) produced no voltage/current violations to size storage against.

**Long-horizon sensitivity-matrix sparsity (T-scaling)**: the sequential-linearization pipeline assembles several `T`-block-diagonal matrices (`AUX_to_all_nodes`, `R_TNd_toNdT`/`R_TNpv_toNpvT`, and the 8+3 `sens.d*` matrices in `build_sensitivity_matrices.m`). MATLAB's `blkdiag` returns a **dense** result unless every input is sparse, so building any of these from dense per-timestep blocks costs `O(T²)` memory/time for what is structurally only `O(T)` real content — this was the confirmed cause of out-of-memory failures beyond ~60-100 day horizons (`T` ≳ 6000-9600). Fixed by making every stage sparse end-to-end:
- `grid/linear_reshape_test.m` (formerly duplicated in `util/`, removed 2026-10-09) builds the reshape permutation directly as `sparse(row_idx, col_idx, 1, ...)` instead of a `zeros(...)` + row-by-row loop.
- `util/repeat_block_diag.m` builds via `kron(speye(m), sparse(matrix))` instead of `blkdiag` of dense copies.
- `util/build_sensitivity_matrices.m` — **superseded by the array restructure** (see the "Done (the O(T²) loop fix)" bullet below). It no longer sparsifies cells + `blkdiag`s; it `pagemtimes`-projects the `[rows x N x T]` arrays and scatters the T reduced blocks with one `sparse(...)` call. The result is the same sparse `T`-block-diagonal — the `T-1` structurally-zero off-diagonal blocks per block-row are still never stored — just built without the dense `blkdiag` intermediate or the per-timestep cell.
- **Gotcha**: once these matrices are sparse, the old sub-threshold clean-up `X(abs(X) < tol) = 0` silently re-densifies — comparing a sparse matrix against a *positive* threshold (`0 < tol`) matches every implicit/structural zero too, forcing MATLAB to materialize a dense logical mask the same size as the matrix. Fixed via `spfun(@(v) v .* (abs(v) >= tol), X)`, which only touches explicitly-stored nonzero entries.
- **Validated**: with all of the above, `main.m` solves end-to-end at `T = 9600` (the `D = 100` WIP horizon above) in ~4 minutes wall-clock (~136s of that inside the Gurobi MILP solve), producing a converged, physically sensible result. This was previously the exact scale that OOM'd.
- **Done (the O(T²) loop fix)**: profiling a `D=365` (`T=35040`) run showed the `for t=1:T` loop in `linear_grid_model.m` growing **linearly per iteration** — 7 ms at t=1 to 156 ms at t=35040 (22×), 48 min total, ~90% of it in the second half. The cause was **allocation count, not byte count**: the loop grew ~10 `{1xT}` cell arrays holding ~350k small dense matrices (~9 GB), and MATLAB's memory manager work scales with the live-allocation count, retriggered by the transient allocs inside `getSCs`/`loadflow_FPIs` every iteration. Fixed by restructuring `gm.lm.*` from cells to **contiguous arrays** (see the `gm.lm` layout note under Key struct layouts): ~350k allocations → ~14. `build_sensitivity_matrices.m` rewritten to consume the 3-D arrays via `pagemtimes` + one `sparse()` scatter (byte-identical output in double; `gm.lm` stored `single`). `re_linearization.m` mirrors the array layout. `util/lm_stack.m` is the `iscell()` shim so `analyze_*` still open pre-restructure result `.mat`. Complex line-current sensitivities `I_dxdP`/`I_dxdQ` (~half the memory) are only stored when `~cfg.solver.current_mag_cstr` (`solve_ess_milp` reads them only in that branch). Memory: ~9 GB → ~2.3 GB default.
- **Done (`getSCs` / `loadflow_FPIs` constant-factor)**: `getSCs.m` now factorizes `A` once (`decomposition(A,'lu')`, reused for the whole-identity solve and the slack-voltage RHS) instead of `2·bigN` per-unit-vector `linsolve` calls — numerically identical to 1e-13. `loadflow_FPIs.m` takes an optional precomputed `YLLi` (constant across timesteps) and no longer builds the unused `H`; `linear_grid_model`/`OPF_verification`/`re_linearization` compute `YLLi` once per loop and pass it. These help the loop's *base* cost; the O(T²) growth above was the dominant term.
- **Not yet touched / open for a future pass toward a full 8760h/T=35040 year**: (1) CVX's own problem-construction overhead (separate from Gurobi's solve time) is untested at `T` in the tens of thousands and is a known CVX weak point for models with millions of scalar variables. (2) The SOE cyclic-boundary constraint (`SOE(end,j) == SOE_0(n,j)` in `solve_ess_milp.m`) spans the *entire* horizon `T`, not per-day — at `T=96` that's a daily cycle, but at `T=9600+` it lets the battery drift for months before returning to baseline, which is a modeling question (not a performance one) worth revisiting before trusting year-scale dispatch results. (3) The ~47 s one-time `fitgmdist` GMM fit in `generate_nodal_scenarios_4` (5 clusters, hits its 100-iteration cap) dominates every short run and is D-independent — cacheable, but that code is a WIP stand-in for the real load-profile source. (4) A per-network **linear-model cache** (save `gm` keyed by `net_id`/`scenario`/`D`/`Ts_h`/`current_mag_cstr`/config-hash, reload for formulation-only studies) is designed but not yet built.

**`gm.lm.Imag0` holds a complex phasor, not a magnitude**: `linear_grid_model.m` stores `Imag0(:,t) = I` (the raw complex branch current, `[L×T]` array). Always wrap with `abs()` before treating it as a current magnitude.

**Temporal diagnostics**: `plot_gm_temporal_profiles(gm, net_id, scenario, fig_dir)` renders a 6-subplot figure (demand/PV/EV/aggregate power in 3-phase kW, voltage in pu, current in pu of ampacity) straight off `linear_grid_model`'s output; called from `util/solve_network_tech_selection.m` right after `preprocess_network(...)`, gated by the `enable_plots` argument threaded down from `main.m`. `old-code/create_temporal_plots.m` is an older, unrelated function with a similar name — it expects a different (`result`) struct that nothing in the current pipeline builds, and is not called anywhere; don't confuse the two.

## Future fixes

Known issues that are recorded but deliberately not fixed yet. Don't fix these unprompted.

- **Slack bus is not always internal node 1 (affects 15 networks, 1 in the portfolio).** The whole pipeline assumes the slack is internal index 1: `get_grid_SFOE.m` drops row 1 (`nodal_demand_all(2:end,…)`), `linear_grid_model.m` uses `YLLi = inv(grid.Y(2:end,2:end))`, and every `N`-space array uses the `+1` shift back to topology ids. But `map_nodes_to_indices.m` numbers nodes by first appearance in `[from; to]` and never forces the slack first; `combined_lv_sub_SFOE.m` only looks it up afterwards (`slack_node_idx = find(...)`). In the single-transformer branch `from_comb` starts with `trafo_rows.From`, so if a transformer is stored with its LV side as `From`, an LV node becomes index 1. Checked 2026-10-07 across all networks (scenario `sc1_2040`): 1099 have `slack_node_idx == 1`, 15 don't, all single-transformer: `LV_Grid_92433` (9), `92545`, `92606`, `92649` (2), `92687` (29), `92697` (23), `92713` (136), `279`, `2076`, `2077`, `2079`, `2082`, `2097`, `2098`, `2102` (all 2). Of these only **`LV_Grid_92713`** is in the 236-network portfolio (`viol_converged_single_tr_ids`). For those networks the load flow holds the wrong node at slack voltage and treats the real slack as a load bus, so their results are physically wrong, not just mislabelled. Proposed fix: have `map_nodes_to_indices` (or `combined_lv_sub_SFOE`) put the slack name first in `node_names`, then number the rest by first appearance as now. That leaves the 1099 correct networks' numbering byte-identical; verify afterwards that every network gives `slack_node_idx == 1`. Until then, treat `LV_Grid_92713` results as suspect.
